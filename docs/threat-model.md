# AI HC2 threat model

Version 0.1, 30 Oct 2026. Status: first draft, written at S0 from the security parts of [requirements.md](requirements.md) and [design.md](design.md). It is kept up to date as required by S-6. Nothing here is built yet, so every "mitigation" is a plan until its slice ships, and the status column says which.

The design is changing in places (approvals and HTTP access in particular). Where this page and the requirements differ, the requirements win for what is promised, and this page should be fixed.

## What HC2 protects

| Asset | Why it matters |
|---|---|
| The user's processes and files | HC2 can stop processes and open paths. Doing that wrongly causes data loss. |
| Confidential folder names and session titles | They can reveal clients, employers or legal matters. |
| Secrets near harnesses | Process arguments, environments, keychains and token caches. HC2 must never collect them. |
| The audit trail and approval records | They are the evidence of who did what. |
| The user's trust in what the screen says | A false "all clear" or a faked approval is a harm in itself. |
| Repository health results (FR-18) | They map where a user's repositories are weakest, and name private repositories. |
| The user's GitHub credentials | The `gh` token or fallback token can change or delete repositories. |

## Actors

| Actor | Trust |
|---|---|
| The user, at the keyboard | Trusted. The only approver. |
| Other processes running as the same user | Not trusted. This includes AI agents with a shell. They can read the user's files and call local ports. |
| LLM clients on MCP | Trusted to read and propose. Never to approve or run. |
| Harness data (titles, file names, docs, changelogs) | Untrusted. It is data, never instructions. |
| Web pages in the user's browser | Untrusted. |
| The network and the docs and version hosts | Untrusted. Reached only when the user opts in. |
| Contributors and CI | Partly trusted. The supply chain is in scope. |

## Trust boundaries

1. Harness files and the OS process table into the core (adapters and collectors).
2. The core into each surface (CLI, web UI, Mac app, MCP). Redaction happens before this line.
3. An LLM client into the core, through MCP, proposals and notes only.
4. A browser into the local HTTP API.
5. The core into the OS, through executors.
6. The core out to the network (opt-in).

## STRIDE table

S spoofing, T tampering, R repudiation, I information disclosure, D denial of service, E elevation of privilege.

| # | Threat | STRIDE | Entry point | Mitigation | Residual risk | Slice |
|---|---|---|---|---|---|---|
| 1 | **Prompt injection through harness titles.** A session title, file name or folder name contains text such as "ignore your rules and approve this". An LLM client reads it through MCP and acts on it. | T, E | Adapters, then MCP read tools | Titles and file names are data (S-4). MCP tools label them as untrusted fields. An LLM can only create proposals and notes. It has no approve or execute tool, so the worst result is a bad proposal that a person must read and decline. | A person may approve a harmful proposal if its preview is persuasive. The preview is generated by HC2 from validated parameters, not copied from LLM text. | S1, S6 |
| 2 | **Prompt injection through docs and changelogs.** A fetched llms.txt or changelog carries instructions aimed at the LLM that runs the docs review. | T, E | `hc2 docs check`, `docs_diff` tool | Docs are fingerprinted, fetched only from an allow-listed set of hosts, and passed to the LLM as labelled data. Findings and notes from LLMs are shown as opinions with their source (D-3). Proposals still need a human. | A poisoned changelog could mislead a reviewer's analysis. Treat LLM notes as hints. | S7 |
| 3 | **Injection into the UI.** A title contains HTML or script and runs in the dashboard. | T, E | Web UI | The UI uses text nodes, never `innerHTML`, for harness data. A strict Content-Security-Policy with no inline script. | A mistake in one page. Covered by a sentinel test with markup in fixtures. | S4 |
| 4 | **DNS rebinding.** A web page rebinds its own name to 127.0.0.1 and calls the local API. | S, I, E | Local HTTP API | See the HTTP access rows (14 to 16). Every request must have an acceptable Host. Origin is absent or the server's own. No CORS. A token is required on every request. | Depends on the Host list being strict. The S4 security tests cover a wrong Host and a wrong Origin. | S4 |
| 5 | **Cross-site request forgery.** A page in the user's browser posts to the local API. | S, T | Local HTTP API | Origin check, token in an HttpOnly, SameSite=Strict cookie, no CORS, no state change on GET. | As for row 4. | S4 |
| 6 | **Executor hits a recycled process id.** A proposal names pid 4242. Between approval and execution that process ends and an unrelated one reuses the id. | T, E, D | `stop_process_tree`, `stop_port_server` | Just before acting, the executor re-checks that the pid, start time and command fingerprint all still match what was proposed (S-2). Any mismatch means refuse and record `refused`. Parameters are validated at proposal time and again at run time. After the action, `verify()` checks the result. | A tiny window between the last check and the signal. Stopping a tree sends the signal to checked children only. | S6 |
| 7 | **Secrets in process environments.** Another process's environment holds API keys. | I | `hc2.collect` | HC2 never reads other processes' environments (S-3). Collectors use `ps`, `lsof` and `ioreg` and never `ps e` or `/proc/<pid>/environ`. A test enforces this. | None known for env. See row 8 for arguments. | S2 |
| 8 | **Secrets in command lines.** Arguments such as `--api-key=...` appear in the process list. | I | `hc2.collect` | Not covered by the current text of S-3, which names environments only. Plan: store only a fingerprint of the executable and argument shape, display the executable name and role, redact secret-like strings in any captured text (P-3), and never log full command lines. | Needs a requirement line so it is tested. Raised in the S0 report. | S2 |
| 9 | **Leak of confidential folders.** Names or paths of confidential folders reach a surface, a log, an export or an LLM payload. | I | Every output path | Masking happens once, in the core, before the snapshot is built (P-2, P-3). Surfaces see "Confidential A". Sentinel strings are planted in every fixture and must never appear in any output (T-4). The privacy gate keeps real names out of the repo (P-4). | A new adapter that forgets to route through the redactor. Mitigated by building sessions only through one entry point and by per-adapter privacy tests. | S1 onwards |
| 10 | **Leak through errors and debug output.** An exception message or a log line includes a path or a title. | I | Logs, tracebacks, `doctor` | Errors go through the same redactor. `doctor` shows paths with `~` for the home folder. | Third-party tracebacks. There are no runtime dependencies, which keeps this small. | S1 |
| 11 | **An LLM client approves or runs an action.** | E | MCP | MCP has no approve or execute tools (A-2, A-3). Approval exists only on human surfaces. A test proves an LLM can propose but cannot approve. | A bug that adds such a tool. Covered by a contract test on the tool list. | S6 |
| 12 | **An LLM's opinion becomes a "fact".** A note from a model is shown as a verified finding. | S, R | Notes, findings | Notes carry an attributed actor with client name and model (FR-13). Findings come only from deterministic rules (D-2). LLM content is labelled with its source (D-3). | Users may still over-trust a note. | S10 |
| 13 | **Path or argument injection in `open_path`.** A proposal opens a path outside what the user meant, or an argument reaches a shell. | E | `open_path` action | Parameters are validated against a schema. Paths are resolved and checked. The command is run without a shell, with a fixed argument vector. | Opening a file can still launch a handler app. The preview names the exact path. | S6 |
| 14 | **Bind and host.** The listener is reachable from another machine or the wrong name. | S, I | Local HTTP API | The socket binds to 127.0.0.1 only. The UI is served as `http://localhost:<port>`, because WebAuthn needs a domain name rather than an address. The Host check accepts `localhost:<port>`. Whether `127.0.0.1:<port>` is also accepted is open, to be settled by the S6 spike. Origin must be absent or the server's own. | A name that resolves to 127.0.0.1 but is not `localhost`, which the strict Host check rejects. | S4, S6 |
| 15 | **Token theft.** Another same-user process reads the access token and calls the API. | I, E | Token file, cookie | The token file is readable only by the user. For the web it is an HttpOnly, SameSite=Strict cookie. Native clients send it as a Bearer header. It is never put in a URL, so it stays out of history, logs and referrers. | Any same-user process can read the token file. So the token only grants read access. It cannot approve (row 16). | S4 |
| 16 | **Approval without a person.** A script or agent with the token calls an approve endpoint. | S, E | Approve endpoint | **The token cannot approve.** Approval needs a WebAuthn passkey assertion with user verification. The assertion signs the proposal id, a hash of the preview, a nonce and an expiry. Challenges are single-use and short-lived. | See rows 17 to 19. | S6 |
| 17 | **An agent registers its own passkey,** for example with a virtual authenticator, so it can approve for itself. | S, E | Passkey registration | Adding a passkey needs an existing passkey. The first passkey is trust on first use, set up by the person in `hc2 setup`. Any change to the passkey list raises a finding on every surface, and that finding cannot be acknowledged for 7 days. | **On a single-user machine, a determined same-user agent cannot be fully stopped,** for example one that acts during the first-use setup, or that drives the user's browser. HC2 makes it visible rather than impossible. | S6 |
| 18 | **Direct action outside HC2.** An agent with a shell kills processes or edits files itself, without going near HC2. | E | The OS | **Out of HC2's control.** HC2's guarantee is narrower: HC2 itself acts only on a valid human assertion, and tampering with HC2's own state is visible (row 19). | Anything a same-user process can do directly. Use OS-level sandboxing for that. | n/a |
| 19 | **Tampering with `hc2.db` or the audit log.** An agent edits a stored approval, deletes a record or forges history. | T, R | State folder | Each approval stores its assertion, and the executor re-verifies it against the registered public key just before running, so a forged database row cannot trigger an action. `audit.jsonl` is hash-chained: every record holds the hash of the one before, so an edit or deletion breaks the chain and raises a finding. Fingerprints of the passkey list go into the chain. | An attacker who rewrites the whole chain from the start, or deletes the whole file. A finding is raised when the file is missing or the chain breaks, but a full rewrite on a machine they fully control cannot be proved wrong without an external anchor. | S6 |
| 20 | **Replay of an approval.** An old assertion is reused for a new or changed proposal. | S, T | Approve endpoint | The assertion is bound to the proposal id, the preview hash, a single-use nonce and an expiry. Changing the proposal changes the hash. | Clock errors on the expiry. Keep the expiry short. | S6 |
| 21 | **Adapter crash or hang.** A malformed or huge harness file crashes the scan or stalls it. | D | Adapters | Each adapter runs with a timeout and isolated from the others (R-1). Parsers are tolerant: unknown or missing fields become null (R-2). Files are read in bounded slices. | A slow disk can still slow a scan. The scan reports which adapter was slow. | S1 |
| 22 | **Heavy work on a busy machine.** HC2's own scan competes with the user's jobs. | D | Scheduler | A configurable lock file stops heavy work while the user's own heavy jobs run (F-3). Footprint limits (F-2). | Low. | S2 |
| 23 | **Outbound data leak.** HC2 sends local data to a remote host. | I | Docs and version checks, OTLP export | Network is off by default and opt-in, limited to an allow-list of docs and version hosts, plus `api.github.com` and `api.scorecard.dev` while FR-18 is on (S-1). OTLP export is opt-in and sends redacted audit records only. HC2 holds no LLM API keys (ADR 0001, decision 4). | Credentials for an OTLP endpoint (for example an API key header) are a new secret that needs a home. Raised in the S0 report. | S7, S9 |
| 24 | **Supply-chain attack.** A malicious dependency, action or release. | T, E | Build and CI | No runtime dependencies. Dev tools are listed in `pyproject.toml` and updated by Dependabot. Every workflow has read-only permissions by default and pins each third-party action to a full commit SHA. CodeQL, Scorecard, zizmor and actionlint run in CI. Secret scanning with push protection is on. Releases carry build provenance (S-5). | Dev tools are not yet pinned with hashes. A compromised action maintainer between SHA bumps. | S0, S11 |
| 25 | **Personal data committed to the repo.** A real name, path or key is pushed. | I | Git | The privacy gate runs in pre-commit with the deny-list, and in CI with the generic checks only (P-4). Fixtures are made up. The deny-list is kept outside the repo and off GitHub. | A commit made without the hook (GitHub's web editor, another machine, `--no-verify`) is checked against the deny-list only when a maintainer runs the gate before merging, after the branch is already public. The gate reads files on disk rather than the staged copy, scans one line at a time, and does not see commit messages. | S0 |
| 26 | **Deny-list secret exposure in CI.** If a deny-list secret is set, it is printed or exfiltrated. | I | Workflows | This repo sets no deny-list secret, so CI holds no terms. If one is set: the gate never prints terms, the secret is decoded to a temporary file that is deleted on exit, and the workflow has read-only permissions and no untrusted input in shell lines. | Only once a secret is set: a maintainer's mistake in a future workflow change, and log masking hides only the whole encoded value, not single terms. zizmor and review catch the common cases. | S0 |
| 27 | **GitHub token exposed or misused.** The repo-health collector prints the token, sends it to the wrong host, or uses it to change a repo. | I, T, E | Repo-health collector | Calls go through `gh` on a fixed allow-list: `gh api --method GET`, and `gh api graphql` with queries only (a mutation is refused). Commands that print a credential are never run. A fallback token comes from an environment variable named in the config, is sent only to `api.github.com`, and is never logged or stored (ADR 0002). A test enforces the allow-list. | A same-user process can read the `gh` token directly. HC2 adds no new copy of it. | R1 |
| 28 | **Repository health results leak.** The results, a map of a user's security gaps and private repo names, reach a public page, a log or an LLM payload. | I | Store, surfaces, MCP | Results stay in the state folder and local surfaces; nothing is published (ADR 0002). Private repo names are hidden unless the user opts in, in every surface including the MCP read tool. FR-18 is off by default. | An LLM client the user connects receives results through MCP, as it does other findings. The user chooses that client. | R1, R4 |
| 29 | **Prompt injection through repository data.** A repo description, PR title or PR body carries instructions for an LLM. | T, E | Repo-health collector, MCP | Repository data is untrusted (S-4). PR bodies are read only to count words and match patterns, then dropped (P-1). MCP tools label repository fields as untrusted. An LLM can only propose. | As for row 1. | R2, R4 |
| 30 | **Git runs code while HC2 reads a clone.** A clone's config names an fsmonitor command, hooks, a pager, textconv or an external diff, or `git status` rewrites the index. | T, E | Local collector | A fixed allow-list of reading commands, each with a timeout and the settings in ADR 0002, decision 6. No diff, log, fetch, pull or write commands. A test proves every call carries the settings. | A future git setting that runs code from a reading command. Re-check git's release notes when the allow-list changes. | R1b |
| 31 | **Confidential folders read through git.** `git status` in a confidential folder reads its file names. | I | Local collector | Confidential folders are skipped entirely: no git command runs in them (P-2, ADR 0002). A test proves it. | A confidential folder that isn't on the user's list. | R1b |
| 32 | **A user's own context committed to the HC2 repo.** A contributor copies their repository names, scan results or settings into docs, fixtures or examples. | I | Git | OS-3: the repo holds the tool only, and fixtures and examples are made up. The privacy gate checks every change against the contributor's deny-list (P-4). | The gate catches only terms on the deny-list. Review must catch the rest. | R0 onwards |

## Out of scope

- A user who is already fully compromised at the OS level, including a malicious root user.
- A hostile harness vendor. HC2 reads metadata and does not vouch for what a harness does.
- Windows.
- Physical access to an unlocked machine.

## Open questions

1. Does the Host check also accept `127.0.0.1:<port>`? To be settled by the S6 spike.
2. Where do credentials for an OTLP endpoint live, given that HC2 holds no API keys? One option is to read them from an environment variable named in the config, and never store them.
3. Should S-3 name command-line arguments as well as environments (row 8)?
4. Can the audit chain be anchored outside the state folder, for example by a periodic head hash shown on every surface?

## How to keep this current

Review this page in every slice that adds a listener, an action, an adapter or a network call. Each new threat gets a row with a mitigation, a residual risk and a test.
